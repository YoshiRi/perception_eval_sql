Specsheet PDF生成パイプライン比較

本アプリで生成する場合と、内部ライブラリ perception_catalog_analyzer / CLI名 awspec を直接使う場合の違い。 JIRA共有用に、要点と図を中心にまとめる。

結論

本アプリ

リリース生成ワークフロー

Evaluator Jobの実行/再利用、成果物DL、trend用metadata/summary作成、topic補正、PDF生成までをまとめて管理する。

awspec直接

ライブラリ標準ワークフロー

既存Job IDを入力し、output/export と output/pdf 配下に標準形式でPDFを生成する。

差分の本質

Appは前処理/管理層

PDF本体の計算・描画は同じライブラリに依存するが、Appはその前後の運用処理を追加している。

補足: この環境では awspec というPython moduleは存在しない。perception_catalog_analyzer.cli 内で定義されたCLI名が awspec。

全体フロー比較

本アプリを使う場合

1. Release Workflow開始 project / target / version / topic / labels / trend metadata を受け取る
2. Evaluator Job準備 Performance / DevOps をschedule、または既存Job/local artifactを再利用
3. App形式に保存 data/release_spec_*/performance, devops にparquet等を配置
4. Trend入力を作成 metadata.yaml, summary.json を保存/検証。DevOps summaryも作成
5. AnalyzerでPDF生成 get_blocks, plot生成, update_template, specsheet

awspec を直接使う場合

1. Job IDを指定 full, usecase, devops job id とmetadata pathを指定
2. 標準path作成 PathManager が output/export, output/pdf を作る
3. Export Performanceは current/future、DevOpsは devops.csv
4. Blocks/Trend生成 metric block、DevOps plot、trend plotを作成
5. PDF出力 specsheet.html と specsheet.pdf を出力

開発者が注意すべき差分

差分影響
AppはJobをschedule/reuseする awspec 直接利用時は基本的にJob IDを用意する必要がある。
Appはtopicを自動検出する 指定topicがない場合、parquet/csv内のtopicへ補正されることがある。
AppはAnalyzer API互換wrapperを使う Analyzerの関数signatureが変わっても壊れにくい。直接利用は現バージョンsignatureに依存。
Appのtrend履歴scan範囲が違う release_spec_* 配下は重複回避のためscan対象外。履歴はstandalone runやtrend_release_*が主。
App生成PDFの本文はPerformance中心 現在のrelease workflowは performance_path に対して evaluation_type="full" で本文を作る。DevOpsはtrend/current plotとして入る。

変更箇所別の注意点

開発したい内容まず見る場所注意点
Release workflowの入力項目を増やす worker/tasks.py の job_run_release_specsheet_workflow Task parameters、metadata保存、run status summaryの3つに同じ情報を通す必要がある。
PDFに出すmetricを変える lib/specsheet_report.py の DEFAULT_SPECSHEET_METRICS / FUTURE_SPECSHEET_METRICS Analyzer側が対応していないmetric名を渡すとblock生成で失敗する。future metricsは future dataframe有無も確認する。
Trend plotを増やす/変える lib/specsheet_report.py の _build_trend_context plot PNGを作るだけでなく、_update_template_compat 経由でtemplate contextに渡す必要がある。
Trend履歴の対象を変える discover_trend_metadata_files release_spec_* をscan対象に戻すと、現在生成中のreleaseが履歴に二重計上される可能性がある。
Topic選択ロジックを変える detect_specsheet_topic_names / resolve_specsheet_topic_name Appは指定topicより実データ内topicを優先する場合がある。直接awspecとの差分になりやすい。
Analyzer libraryを更新する _scene_dataframe_from_dir_compat, _get_blocks_compat, _update_template_compat, _specsheet_compat Appはsignature差分を吸収している。library更新時はwrapperが新旧どちらにも対応しているか確認する。
DevOps表示を変える _write_devops_trend_summary と load_devops_trend_data DevOps summaryはnested dict構造。passed/total の階層を変えるとtrend分類・plot生成に影響する。
出力先や静的linkを変える lib/release_specsheet_library.py と import script PDF生成場所とUI表示用/static公開場所は別。片方だけ変えるとJIRA/画面リンクが切れる。

開発時の確認順序

1. 入口 worker/tasks.py で入力parameterとmetadataが期待通りか確認
2. Artifact performance/, devops/ にparquet, csv, summaryができるか確認
3. Topic/CSV resolve_specsheet_topic_name と ensure_specsheet_csvs の結果を確認
4. Blocks specsheet/resources/summary.json がfullとして分類されるか確認
5. PDF trend_assets/*.png, specsheet.html, specsheet.pdf を確認
