Data & Reports

What a run is made of, and what you can export from it.

Every view in the dashboard traces back to a handful of files inside a run folder. This chapter maps the folder anatomy, the caches the app builds on top, and the exportable documents: the Evaluation Dashboard Report PDF, the LLM analysis package, and the CSV/JSON exports scattered through the pages.

Run Folder Anatomy

One directory per run, under the data root.

The data root is EVAL_DASHBOARD_DATA_ROOT (default ./data, /app/data in Docker). Two shapes exist: plain runs, and release containers whose role children (performance / usecase / devops) each count as a selectable run named like [REL] <version> | <Role> | <date>. 

data/
├── my_eval_run/                     # a plain run
│   ├── Summary.csv                  # TP & kinematics rows  → Overview, TP Summary
│   ├── Score.csv                    # criteria blocks       → Criteria Based Score
│   ├── scene_result.parquet         # detection frames      → Detection Stats, viewers
│   ├── future.parquet               # prediction tracks     → Prediction Evaluation
│   ├── metadata.yaml                # owner, task, evaluator job info
│   └── .dashboard_cache/            # derived caches (auto-built, auto-invalidated)
│
├── my_release/                      # a release container
│   ├── metadata.yaml                # tags, pilot_auto_version, data_count, date…
│   ├── performance/                 # role runs, each parquet + summary.json + metadata
│   ├── devops/
│   ├── usecase/                     # optional
│   └── specsheet/                   # generated spec-sheet PDFs + trend assets
│
└── some_tlr_result/                 # TLR: any folder containing result.json
    └── result.json                  # JSONL, one line per frame → TLR Analysis
Caches you may notice

Detection Stats materializes a flattened eval_flat cache parquet per run (per polygon setting); Prediction Evaluation writes .dashboard_cache/prediction_eval_cache/ (three summary parquets + manifest, rebuilt when future.parquet changes). Both are safe to delete — they regenerate.

Export 1

Evaluation Dashboard Report (PDF).

One A4 PDF that mirrors the four main analysis pages for the runs and label filters currently selected on Overview. Generated by the Generate Evaluation Dashboard Report button on Overview; the download stays valid only while the selection matches — change a run or filter and you regenerate.

SECTION 1

Overview

Metric cards (TP mean, XRMS/YRMS/XSTD/YSTD per run) and TP-mean-by-label figures.

SECTION 2

TP Summary

Metrics table plus distributions/violins — or per-candidate delta figures in compare mode.

SECTION 3

Criteria Score

Criteria tables and figures, compare deltas, spider comparisons.

SECTION 4

Detection Stats

KPI table, status distributions, distance panels; diff / lens figures in compare mode.

Sections degrade gracefully

A run without Summary.csv skips the TP section with a note; missing Score.csv skips Criteria; no compatible parquet skips Detection Stats. A figure that cannot be rasterized becomes a note instead of aborting the PDF. PDF chart export uses Plotly/Kaleido and needs Chrome — the Docker image includes it.

Export 2

LLM analysis package (ZIP).

On Detection Stats, Prepare LLM report ZIP bundles the evidence tables for a baseline-vs-candidate comparison plus prompt files, and the page shows a paste-ready prompt. The bundled instructions ask an LLM for an 11-section regression report: executive summary, KPI dashboard, distance and class analysis, TP improvement / FP increase hotspots, safety-critical regressions, localization quality, root-cause hypotheses, and a recommendation.

Housekeeping

Data Management: list, share, package, delete.

Data Management
  • Runs in data root — name, size, modified time, and ✓/— for Summary.csv / Score.csv / parquet.
  • Share — compose the exact Overview query string for a single run or an A/B pair.
  • Download — lazy ZIP of a run’s generated artifacts (built on demand, dropped when you switch runs).
  • Delete — permanent, type-the-name confirmation, restricted to run directories under the data root.
Shared server etiquette

Delete frees disk for everyone — and removes the run for everyone. The Workflow page’s Local Runs tab offers the same delete with the run’s ownership metadata visible; prefer it when unsure whose run it is.

When Data Looks Wrong

Inspect the artifact itself.

Parquet Debug opens any parquet (schema, filtered previews, column stats, ad-hoc DuckDB SQL), PKL (structure tree, embedded DataFrames), or TLR result.json (criteria table, success timeline, status heatmap) without leaving the app.
