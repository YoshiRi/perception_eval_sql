# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository overview

Two independent sub-projects share this repo:

1. **Grafana + DuckDB viewer** (repo root) — SQL views over `.parquet` / `.csv` files, served via a custom Grafana Docker image.
2. **Streamlit evaluation dashboard** (`evaluation_dashboard_app/`) — Python app for downloading evaluation results, generating summary CSVs, and visualising them.

A third layer, **safety metrics scripts** (`script/`, `configs/`), provides a standalone Python pipeline for computing NuScenes-inspired safety-critical detection metrics from `current.csv`.

`data/` is gitignored entirely.

## Data model

### `current.csv` (primary analysis source)

Produced by `perception_eval`. Each row is one object at one timestamp. The two main roles:

| `source` | `status` | meaning |
|----------|----------|---------|
| `GT` | `TP` | ground-truth object that was detected |
| `GT` | `FN` | ground-truth object that was missed |
| `EST` | `TP` | detection matched to a GT |
| `EST` | `FP` | detection with no GT match |

Key columns: `unix_time`, `frame_index`, `x`, `y`, `label`, `confidence`, `visibility`, `x_error`, `y_error`, `yaw_error`, `speed_error`, `r` (distance bin string e.g. `"20-40"`), `theta` (angle bin).

`visibility` is only populated for GT rows: `FULL` / `MOST` / `PARTIAL` / `NONE`.  
Error columns (`x_error` etc.) are only populated for TP rows.  
**Matching granularity is `unix_time`** (~26k unique timestamps, median ~33 objects each). `frame_index` groups many timestamps into a scenario.

### Streamlit dashboard data (`evaluation_dashboard_app/data/`)

| file | content |
|------|---------|
| `Summary.csv` | Per-scenario: `id`, `TP`, `xstd`, `xrms`, `ystd`, `yrms`, `vx`, `vy`, `perception_label`, `product_label` |
| `Score.csv`   | Criteria blocks: `Scenario`, `Option`, `GT_OBJ`, then repeating groups of `Distance`, `NM`, `TP/TN`, `ADD`, … per criteria index |
| `*.parquet`   | Full detection data; columns vary by run (use `parquet_schema.schema_flags()`) |

`Summary.csv` and `Score.csv` are generated by running `perception_eval` (requires ROS2 pilot-auto environment).

## Architecture: Streamlit app

### Data flow

```
Download page (6_Download.py)
  → downloads ZIP / result JSON from evaluator API
  → optionally runs perception_eval to produce Summary.csv + Score.csv
  → stores under data/<run_name>/

Overview.py
  → lib/run_loader.load_run(path) → { path, summary, score }
  → sets st.session_state["runA"], ["runB"], ["all_runs"], ["run_labels"]
  → all other pages read from session_state (no re-load)
```

### Key library modules (`evaluation_dashboard_app/lib/`)

| module | role |
|--------|------|
| `run_loader.py` | Loads `Summary.csv` + `Score.csv` into a run dict; parquet-only runs are also supported |
| `path_utils.py` | Resolves `EVAL_DASHBOARD_DATA_ROOT` env var; enforces path traversal guard |
| `db.py` | Postgres task store for the worker queue (used only when `USE_TASK_QUEUE=true` + `DATABASE_URL` set) |
| `task_queue.py` | Redis/RQ enqueue + reconciliation; gracefully degrades when Redis is absent |
| `parquet_schema.py` | DuckDB-based schema introspection; returns `schema_flags` dict so pages show/hide features |
| `criteria_absolute_gates.py` | Threshold-based pass/fail evaluation over `Score.csv` criteria blocks |
| `page_chrome.py` | Shared Streamlit UI helpers (hero, section headers, share links, styles) |

### Production worker queue

When `USE_TASK_QUEUE=true` + `DATABASE_URL` + `REDIS_URL` are set, heavy operations (download, eval, parquet build) are offloaded to an RQ worker. Task state is persisted to Postgres. Streamlit polls `db.get_task()` for progress. The worker entry point is `worker/run_worker.py`.

### Deployment-only page (`pages/99_Deployment_Debug.py`)

Only functional inside Docker. Controlled by `EVAL_DEPLOYMENT_DEBUG_*` env vars. `inject_app_page_styles()` hides its sidebar link when not in Docker.

## Architecture: safety metrics scripts

```
configs/*.yaml          ← evaluation parameters (classes, dist_max_m, visibility_exclude, …)
script/
  safety_metrics/
    config.py           ← SafetyConfig dataclass; YAML load/save; CLI arg registration
    compute.py          ← pure functions: prepare(), compute_recall(), compute_ap_table(),
                          compute_tp_metrics(), compute_nds(), run_all()
  run_safety_metrics.py ← CLI: loads CSV → calls run_all() → prints + saves results
```

`compute.py` has no I/O. The NDS formula used is an adaptation of the nuScenes NDS:
```
NDS_safety = 1/8 × (5×mAP + ATE_score + AOE_score + AVE_score)
TP score_i = 1 − min(metric_i / norm_i, 1.0)   # note: normalised, unlike official nuScenes
```

See `design.md` for the full formula rationale, deviation from official nuScenes, and score interpretation guide.

## SQL views (Grafana/DuckDB)

Views in `sql/` use Grafana variable interpolation syntax (`${var:sqlstring}`). They are not runnable standalone without substituting variable values.

`view_eval_flat.sql` — the base view used by most panels. Reads a parquet file, computes `dist_h = sqrt(x²+y²)`, joins to fixed 10m distance bins (0–150m+), adds boolean `is_tp/is_fp/is_fn` columns.

`view_tpr_fpr.sql` — aggregates TP/FP counts by `(t4dataset_id, topic_name, label, distance_bin, visibility)`, computes `tpr` and `fpr`.
